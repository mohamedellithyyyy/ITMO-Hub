\section{Нормальные формы}


\textbf{1NF.} Отношение находится в 1NF, если все его атрибуты содержат только
атомарные значения и каждая строка уникальна. Все атрибуты схемы атомарны
(\texttt{VARCHAR}, \texttt{INTEGER}, \texttt{DATE}), повторяющихся групп нет,
каждая таблица имеет первичный ключ. Схема находится в~\textbf{1NF}.


\vspace{5pt}
\textbf{2NF.} Отношение находится во 2NF, если оно находится в 1NF и
отсутствуют частичные зависимости неключевых атрибутов от первичного ключа.
Частичная зависимость возможна только при составном ключе. Единственное
отношение с составным ключом ---
\texttt{person\_hall(person\_id,\,hall\_id)} ---
не имеет неключевых атрибутов, поэтому частичная зависимость невозможна.
Во всех остальных отношениях ключ простой (суррогатный \texttt{SERIAL}),
что исключает частичные зависимости по определению.
Схема находится в~\textbf{2NF}.

\vspace{5pt}
\textbf{3NF.} Отношение находится в 3NF, если оно находится во 2NF и
отсутствуют транзитивные зависимости неключевых атрибутов от первичного
ключа. Транзитивная зависимость означает: $K \to A \to B$, где $A$ не
является ключом. В данной схеме ни один неключевой атрибут не детерминирует
другой неключевой атрибут: внешние ключи (\texttt{campus\_id},
\texttt{hall\_id}, \texttt{mentor\_id} и~др.) являются атомарными ссылками
и не порождают цепочек зависимостей внутри своих отношений.
Схема \textbf{уже удовлетворяет 3NF}, поэтому декомпозиция не потребовалась.
Состав функциональных зависимостей по сравнению с исходной схемой
не изменился.

\section{BCNF}

Отношение находится в BCNF, если для каждой нетривиальной функциональной зависимости X → Y, X является суперключом.

Все таблицы моей схемы удовлетворяют BCNF. Большинство таблиц имеют один кандидатный ключ (id), поэтому BCNF выполняется автоматически.

Особого внимания требуют mentorship и teaching, они имеют по два кандидатных ключа. В mentorship детерминанты mentorship_id и (mentor_id, ward_id) — оба являются суперключами. В teaching детерминанты teaching_id и (person_id, subject_id)  оба являются суперключами. Нетривиальных ФЗ с детерминантом, не являющимся суперключом, нет. Схема находится в BCNF.

\section{Денормализация}

\noindent\textbf{Добавление счётчика дверей в таблицу} \texttt{hall}.
Если часто запрашивается количество дверей в конкретном зале, можно добавить
атрибут \texttt{door\_count INTEGER DEFAULT~0} в таблицу \texttt{hall}.
Это позволит избежать операции \texttt{COUNT(*)} при каждом запросе.
Необходимо обновлять этот атрибут при добавлении или удалении дверей ---
это решается триггером (реализован в разделе~6).

\vspace{5pt}
\noindent\textbf{Добавление названия кампуса в таблицу} \texttt{hall}.
Запросы вида <<список залов с названием кампуса>> встречаются часто.
Без денормализации они требуют соединения \texttt{hall\,JOIN\,campus}.
Добавление поля \texttt{campus\_name} \texttt{VARCHAR(100)} в \texttt{hall}
позволяет обойтись одним сканированием таблицы. При переименовании
кампуса значение должно обновляться в обеих таблицах.

\vspace{5pt}

\section{Функция на языке PL/pgSQL}

Функция автоматически поддерживает счётчик \texttt{door\_count} в таблице
\texttt{hall}: при добавлении двери счётчик увеличивается на~1, при
удалении --- уменьшается на~1, при переносе двери в другой зал ---
корректируется у обоих залов.

\vspace{4pt}
\noindent\textit{Подготовка: добавление столбца и инициализация.}

\begin{lstlisting}
ALTER TABLE hall ADD COLUMN IF NOT EXISTS door_count INTEGER DEFAULT 0;

UPDATE hall h
SET    door_count = (
           SELECT COUNT(*)
           FROM   door d
           WHERE  d.hall_id = h.hall_id
       );
\end{lstlisting}

\noindent\textit{Триггерная функция.}

\begin{lstlisting}
CREATE OR REPLACE FUNCTION trg_update_door_count()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE hall
        SET    door_count = door_count + 1
        WHERE  hall_id = NEW.hall_id;
        RETURN NEW;

    ELSIF TG_OP = 'DELETE' THEN
        UPDATE hall
        SET    door_count = door_count - 1
        WHERE  hall_id = OLD.hall_id;
        RETURN OLD;

    ELSIF TG_OP = 'UPDATE' THEN
        IF OLD.hall_id IS DISTINCT FROM NEW.hall_id THEN
            UPDATE hall
            SET    door_count = door_count - 1
            WHERE  hall_id = OLD.hall_id;

            UPDATE hall
            SET    door_count = door_count + 1
            WHERE  hall_id = NEW.hall_id;
        END IF;
        RETURN NEW;
    END IF;

    RETURN NULL;
END;
$$;
// Создание триггера
CREATE OR REPLACE TRIGGER trg_door_count
AFTER INSERT OR UPDATE OR DELETE
ON door
FOR EACH ROW
EXECUTE FUNCTION trg_update_door_count();
\end{lstlisting}
